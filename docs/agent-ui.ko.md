# 대화로 만드는 탭

[English](agent-ui.md) · **한국어**

사용자는 곁 앱에서 에이전트와 대화하는 것만으로 새 탭을 만들고, 그 안을 원하는 부품으로 채우고, 데이터를 연결한다. 예를 들어 앱과 광고로 수익을 내는 사용자가 "앱스토어 매출이랑 광고 수익을 한눈에 보는 탭 만들어 줘"라고 말하면, 에이전트가 수익 탭을 설계하고 매일 숫자를 채운다. 무엇을 보여 줄지는 정해져 있지 않다. 이번 달 합계를 크게 볼 수도 있고, 출처별 막대를 볼 수도 있고, 둘 다 볼 수도 있다. 조합은 사용자가 대화로 정한다.

앱은 에이전트가 무엇을 하는지 모른다. 앱이 아는 것은 부품 목록과 그 부품을 그리는 방법뿐이다. 수익이 무엇인지, 어디서 가져오는지는 에이전트의 일이다. 이것이 곁의 원칙인 "앱은 에이전트가 쓸 일반 부품만 둔다"를 화면에 적용한 모습이다.

## 누가 무엇을 맡나

| 부분 | 맡는 일 | 모르는 것 |
|---|---|---|
| 앱 | 부품 목록(카탈로그)과 각 부품을 그리는 코드. 설계도를 받아 화면을 그린다. 탭을 몇 개 보일지 사용자가 고르는 화면 | 데이터의 뜻, 데이터를 어디서 가져오는지 |
| 덱 서버 | 설계도와 데이터를 사용자별로 저장하고, 판을 남기고, 형식을 검사한다. 카탈로그를 에이전트에게 내보낸다 | 에이전트의 종류 |
| 에이전트 | 대화로 사용자가 원하는 화면을 알아내고, 카탈로그를 보고 설계도를 짜고, 외부 서비스에서 데이터를 가져와 넣는다 | 앱 내부 코드 |
| 에이전트별 연결부 | 그 에이전트가 카탈로그를 읽고 설계도를 올리기 쉽게 해 주는 얇은 층. Hermes 라면 스킬 하나 | 없음. 선택 사항이다 |

서버와 에이전트는 사용자가 직접 등록해서 쓰므로, 제품의 중심은 앱의 모듈화와 카탈로그다. 연결부는 에이전트마다 있어도 되고 없어도 된다. 카탈로그만 있으면 어떤 에이전트든 설명서를 읽고 설계도를 짤 수 있다.

## 부품

부품은 앱 코드에 하나씩 등록한다. 등록할 때 이름, 받는 값의 형식, 짧은 설명을 함께 적고, 이 셋이 그대로 카탈로그가 된다. 부품을 그리는 코드와 카탈로그가 한 곳에서 나오므로 둘이 어긋나지 않는다.

1단계에서 넣을 부품은 아래와 같다. 이것으로 수익, 할 일, 습관, 운동 기록처럼 숫자와 목록으로 된 화면은 대부분 만들 수 있다.

그래프는 SVG 없이 앱의 기본 뷰만으로 그린다. 폰의 개발 빌드를 다시 만들지 않으려고 네이티브 의존성을 더하지 않았다.

부품 안에서 눈에 보이는 것은 설계도로 바꿀 수 있다. 색은 `color` 로 정하는데, 테마를 따라가는 이름(`accent`, `ok`, `warn`, `danger`, `neutral`, `blue`, `purple`, `teal`, `coral`, `green`, `yellow`)을 쓰면 라이트와 다크 모두에서 읽히고, 꼭 필요하면 `#RRGGBB` 도 받는다. 범례나 눈금, 퍼센트, 비교 문구처럼 켜고 끌 수 있는 요소는 `show…` 로 시작하는 참거짓 값이고, 숫자 자릿수는 `decimals`, 정렬은 `sort` 다. 목록 칸 안에서는 항목마다 `color`, 이름 옆에 붙는 `tags`, 순위표의 `accent` 를 쓸 수 있다. 옵션을 하나도 쓰지 않으면 지금 모양 그대로 그려진다. 부품마다 어떤 옵션이 있는지는 카탈로그가 원본이다.

서버는 설계도를 올릴 때 이름을 대소문자까지 정확히 맞춰 보고, 모르는 이름과 `null` 값은 거절한다. 숫자는 뜻에 맞는 범위만 받는다. `decimals` 는 0~10, `limit` 는 1~100, `highlight` 는 0~100 의 정수이고 `ratio` 는 0.25~4 다. 그 밖의 숫자는 절댓값 10¹⁵ 까지다. `image` 와 `link` 의 `url` 은 `https://` 주소만 받는다. 목록 칸의 원소는 카탈로그의 `fields` 에 있는 이름만 가진 객체여야 하고, `fields` 가 없는 칸(`labels`, `columns`, 표의 `rows`)은 글이나 숫자, 또는 그 배열이다.

부품에 `link` 를 달면 누를 때 덱의 다른 화면이 열린다. `{"to": "costs", "period": "week"}` 처럼 기본 화면(`costs`, `routines`, `rooms`, `approvals`)이나 같은 에이전트의 화면 id 를 가리키고, 제목 끝에 작은 꺾쇠가 붙는다. 목록 줄이나 순위 줄처럼 칸마다 다른 곳으로 가야 하면 칸 안에 `link` 를 둔다. 여는 규칙은 앱 한 곳(`app/src/ui/link.tsx`)에 있다. 탭 막대에 있으면 그 탭으로 가고, 탭 밖이나 숨김이면 화면으로 연다. 아직 없는 기본 화면은 견본으로 잠깐 열고 「탭에 두기」로 추가할 수 있게 한다. 없는 에이전트 화면이면 「없는 화면이에요」와 함께 에이전트에게 다시 만들어 달라는 버튼을 보인다.

화면은 탭 막대, 탭 밖, 숨김 중 한 자리에 놓인다. 에이전트는 화면을 올릴 때 `place` 로 자리를 정한다. 결산 화면에서 링크로만 들어가는 상세 화면은 `hidden` 으로 두어 탭 칸을 아낀다. 사용자가 링크가 걸린 화면을 지우려 하면 어느 화면에서 링크가 오는지 확인창에 알린다.

지금 앱에 있는 방, 루틴, 비용 화면도 큰 부품(`rooms`, `routines`, `costs`)으로 카탈로그에 올린다. 이 셋은 덱이 이미 가진 데이터를 쓰고 기간 넘기기 같은 자체 동작을 갖고 있어서, 작은 부품으로 쪼개지 않고 통째로 하나의 부품이 된다. 이렇게 하면 기본 탭과 에이전트가 만든 탭이 같은 방식으로 그려진다.

같은 모양이 여러 탭에 반복되면 에이전트는 그것을 조립 부품으로 뺄 수 있다. 조립 부품은 기본 부품 여러 개를 묶어 이름을 붙인 틀이다. `ui.part.put` 으로 `{version, id, title, params, blocks}` 를 올리고, 값 자리에 `{"$param": 이름}` 을 둔다. 화면에서는 `{"type": "use", "part": id, "with": {...}}` 한 칸으로 부른다. 서버가 화면을 앱에 줄 때 `use` 를 부품의 blocks 로 펼치므로 앱은 `use` 를 보지 못하고, 옛 판 앱도 그대로 그린다. 에이전트의 `ui.list` 에는 원문이 그대로 돌아온다.

매개변수의 `kind` 는 그 자리 속성의 kind 와 같아야 하고, 선언했는데 쓰지 않은 매개변수와 부품 안의 `use` 는 거절된다. `with` 에서 `required` 는 꼭 주어야 하고 빠진 선택 값은 `default`, 그것도 없으면 그 속성을 뺀다. 값으로 `{"$data": ...}` 도 받는다. 부품을 새 판으로 올리면 쓰는 화면이 모두 바뀌고, 쓰는 화면이 하나라도 새 판으로 펼쳐지지 않으면 올리기를 거절한다. 쓰는 화면이 있는 부품은 지울 수 없다. 한도는 카탈로그 `parts` 절에 있다. 에이전트마다 20개, 매개변수 1~12개, blocks 1~20개이고 펼친 화면도 기본 한도(60개, 64KB)를 지킨다.

에이전트에게 주는 안내는 셋이다. 같은 모양이 두 탭 이상에서 반복될 때만 부품으로 빼고, 매개변수에는 탭마다 바뀌는 값만 두고, 부품을 고치면 쓰는 화면이 다 바뀐다는 것을 사용자에게 먼저 알린다. 사용자는 탭 편집 맨 아래 「조립 부품」에서 부품마다 쓰는 탭을 보고, 상세 화면에서 `sample` 로 펼친 미리 보기(`GET /api/agents/{id}/ui/parts/{pid}/preview`)와 고친 기록을 본다. 쓰는 탭이 없는 부품만 거기서 지울 수 있다.

부품 모양은 앱의 테마를 따른다. 에이전트는 색이나 글자 크기를 정하지 않는다. 그래야 누가 만든 탭이든 앱과 한 몸처럼 보이고, 라이트와 다크, 한국어와 영어가 저절로 맞는다.

## 설계도

설계도는 탭 하나를 설명하는 JSON이다. 에이전트는 이것만 만든다.

```json
{
  "version": 1,
  "id": "revenue",
  "title": "수익",
  "icon": "chart.line.uptrend.xyaxis",
  "blocks": [
    { "type": "stat", "label": "이번 달", "value": { "$data": "revenue.month.total" }, "unit": "KRW",
      "compare": { "$data": "revenue.month.prev" }, "better": "up" },
    { "type": "bars", "title": "하루씩", "items": { "$data": "revenue.daily" } },
    { "type": "hbars", "title": "어디서 벌었나", "items": { "$data": "revenue.bySource" } },
    { "type": "button", "label": "지금 다시 계산", "say": "수익 탭 숫자 지금 다시 계산해 줘" }
  ]
}
```

값 자리에 숫자를 바로 써도 되고, `{ "$data": "…" }`로 데이터 묶음의 한 칸을 가리켜도 된다. 화면 모양과 숫자를 나눠 두면, 매일 아침 숫자만 바뀔 때 설계도를 다시 보낼 필요가 없다.

## 데이터

데이터는 세 곳에서 온다.

첫째는 에이전트가 넣는 데이터 묶음이다. 이름(`revenue`)을 붙인 JSON 하나이고, 에이전트가 외부 서비스에서 가져와 계산한 결과를 통째로 넣는다. 앱스토어 매출, 광고 수익, 은행 잔액처럼 외부 인증이 필요한 데이터는 모두 이 길로 온다. 그래서 앱과 덱 서버는 외부 서비스의 인증 정보를 갖지 않는다. 갱신은 에이전트의 루틴이 맡는다. 사용자가 "매일 아침 8시에 갱신해 줘"라고 말하면 에이전트가 루틴을 만든다.

둘째는 덱이 이미 아는 데이터다. 비용, 루틴, 대화 수처럼 덱 서버에 있는 값은 `deck.costs.daily` 같은 이름으로 바로 가리킨다. 에이전트가 따로 넣지 않아도 늘 최신이다.

셋째는 설계도에 직접 쓴 값이다. 목표 금액처럼 잘 바뀌지 않는 값에 쓴다.

데이터 묶음에는 갱신 시각이 붙는다. 앱은 탭 아래에 "3시간 전 갱신"을 보여 주고, 너무 오래되면 흐리게 표시한다.

## 탭 배치

탭은 에이전트마다 따로 가진다. 사이드바에서 에이전트를 바꾸면 탭 막대도 그 에이전트의 탭으로 바뀐다. 회사 일을 하는 에이전트와 개인 일을 하는 에이전트가 서로 다른 화면을 갖는 셈이다. 탭은 덱 서버에 저장하므로 아이폰이든 다른 기기든 같은 에이전트를 고르면 같은 탭이 보인다. 그래서 탭에 "누가 만들었는지"를 따로 표시하지 않는다. 그 에이전트의 탭은 그 에이전트가 만들고 고친다.

화면 아래 탭 막대에는 최대 다섯 개를 보인다. 홈은 늘 첫 칸이고 숨길 수 없다. 잘못 만든 탭 때문에 앱을 못 쓰게 되는 일을 막기 위해서다. 나머지 네 칸은 그 에이전트의 탭 중에서 사용자가 고른다. 새 에이전트를 등록하면 방, 루틴, 비용 견본이 처음부터 들어 있다.

고르는 곳은 설정의 "탭 편집"이다. 보일 탭을 켜고 끄고, 끌어서 순서를 바꾼다. 탭 막대에 오르지 않은 탭은 홈 위 칩 줄이나 탭 편집의 "탭 밖"에서 연다. 에이전트가 새 탭을 만들면 빈 칸이 있을 때만 탭 막대에 오르고, 칸이 다 찼으면 탭 밖에 두며 `ui.ack` 의 `reason` 으로 그 사실을 알린다. 에이전트는 그 이유를 대화로 사용자에게 전한다.

탭 아이콘은 iOS 시스템 아이콘(SF Symbols)의 이름으로 받는다. 지금은 앱을 기준으로 하고, 나중에 웹을 붙이면 시스템 아이콘 이름을 웹 아이콘으로 바꾸는 대응표를 두고 대응이 없으면 기본 아이콘을 쓴다.

iOS 시스템 탭 막대는 탭 칸을 코드에 미리 적어 둬야 한다. 그래서 에이전트 탭용 칸 네 개를 미리 만들어 두고, 쓰는 칸만 보이게 한다. 칸을 숨기거나 드러내면 탭 막대가 다시 그려지면서 보던 화면 상태가 처음으로 돌아간다(expo-router 타입 설명에 적힌 동작). 탭 구성은 자주 바꾸는 일이 아니라 받아들인다.

## 견본

에이전트에게 말하지 않고도 탭을 더할 수 있게, 앱에 견본 탭 몇 개를 넣어 둔다. 견본은 설계도 한 장이다. 사용자가 탭 편집의 "탭 추가"에서 견본을 고르면 그 설계도가 지금 에이전트의 탭으로 복사된다. 복사한 뒤에는 보통 탭과 같아서, 에이전트에게 "비용 탭에 이번 달 예산 진행 막대 넣어 줘"처럼 고쳐 달라고 할 수 있다.

방, 루틴, 비용, 오늘 한눈에는 덱 데이터만 쓰므로 고르는 즉시 숫자가 나온다. 내 컴퓨터는 곁의 센서가 세 묶음을 올리므로 역시 설정이 없다. 네트워크는 20초마다 재고 5분마다(상태가 바뀌면 바로) `netwatch` 를, 디스크는 10분마다 `disk` 를, CPU와 메모리, 스왑, 배터리는 30초마다 `system` 을 올린다. `system` 의 `status` 는 CPU 85% 이상과 메모리 90% 이상을 warn, 배터리 20% 이하를 warn, 10% 이하를 danger, 배터리가 없으면 off 로 둔다. 서버는 묶음마다 따로 재므로 앱 견본만 한 화면으로 합친다. 센서는 `KYEOT_SENSORS=off` 로 끈다. 나머지는 계약 견본이다. 모양만 있는 빈 틀이고, 탭 안의 "에이전트에게 채워 달라고 하기" 버튼이 표의 묶음 이름과 예시 모양을 부탁 문구에 붙여 보낸다. 에이전트가 묶음을 올리면 서버가 그 묶음을 쓰는 설계도의 `$data` 경로와 대조해, 경로가 없거나 숫자 자리에 숫자가 아니거나 목록 칸에 카탈로그 `fields` 에 없는 키가 있으면 저장은 하고 `ui.ack` 의 `reason` 으로 알린다. 표는 앱의 `app/src/ui/templates.ts` 에서 `node scripts/gen-template-docs.mjs` 로 만든다.

## 에이전트가 배우고 올리는 법

덱 서버는 카탈로그를 두 길로 내보낸다. 하나는 에이전트가 접속할 때 보내는 첫 메시지에 카탈로그 판 번호를 싣는 것이고, 다른 하나는 `GET /ui/catalog`로 전체를 읽게 하는 것이다. 카탈로그에는 부품 목록과 설계도 예시, 지켜야 할 규칙(크기 한도, 탭 수 한도)이 들어 있다.

에이전트는 설계도와 데이터 묶음을 프로토콜 메시지 `ui.put`, `data.put`으로 올린다. 덱 서버는 받은 설계도를 카탈로그로 검사한다. 모르는 부품이나 너무 큰 설계도는 이유를 붙여 거절하고, 에이전트는 그 이유를 보고 고쳐서 다시 올린다.

Hermes 처럼 덱 프로토콜을 직접 말하지 않는 에이전트는 브리지가 대신한다. 브리지는 맥 안에서만 열리는 작은 주소를 두고, 에이전트가 거기에 설계도를 보내면 덱 서버로 넘긴다. Hermes에게는 이 주소와 카탈로그 읽는 법을 적은 스킬 하나(`deck-ui`)를 준다. 스킬은 실행 파일에 들어 있어서, 브리지가 화면 주소를 열고 붙을 때 Hermes 폴더에 깔고 깔린 판이 낮으면 옛 파일을 `SKILL.md.bak-<시각>` 으로 남기고 바꾼다. 스킬이 없어도 에이전트가 카탈로그 주소를 알면 같은 일을 할 수 있다.

## 안전

에이전트는 설계도만 보낸다. 앱은 카탈로그에 있는 부품만 그리므로, 에이전트가 앱 안에서 코드를 실행할 길이 없다. 덱 서버는 설계도와 데이터를 주인별로 나눠 저장하고, 에이전트는 자기 주인의 탭만 고칠 수 있다. 설계도 크기와 데이터 묶음 크기에는 한도를 둔다.

설계도는 고칠 때마다 판을 남긴다. "어제 모양으로 되돌려 줘"라고 하면 에이전트가 이전 판을 다시 올리고, 설정의 탭 편집에서도 이전 판을 고를 수 있다.

## 직접 만드는 부품

기본 부품으로 부족해지면 두 단계로 넓힌다.

먼저 조립 부품이다. 기본 부품 여러 개를 묶어 이름을 붙인 틀로, 예를 들어 "수익 카드"는 큰 숫자와 막대 하나와 버튼 하나를 묶은 것이다. 에이전트가 틀을 만들어 두면 여러 탭에서 같은 모양을 다시 쓸 수 있다. 결국 기본 부품의 조합이라 코드 실행이 없고 안전하다.

그다음 격리 부품이다. 에이전트가 HTML과 자바스크립트로 쓴 부품을 격리된 웹뷰에서 그린다. 웹뷰는 앱의 토큰이나 다른 화면에 손댈 수 없고, 정해진 통로로 데이터 묶음만 받는다. 기본 부품으로 표현할 수 없는 화면(지도, 달력 격자, 특이한 차트)을 위한 탈출구다. 자유도가 가장 높은 대신 테마와 언어를 부품이 스스로 맞춰야 하므로, 카탈로그에 그 규칙을 적어 둔다.

## 단계

| 단계 | 끝나면 되는 것 | 손대는 곳 |
|---|---|---|
| 1 | 방, 루틴, 비용이 견본 설계도로 그려지고, 탭이 에이전트별로 바뀌고, 탭 편집에서 보일 탭과 견본을 고른다. "수익 탭 만들어 줘"라고 하면 에이전트가 기본 부품과 직접 쓴 숫자로 탭을 만든다 | 앱(부품 등록, 그리기, 탭 칸, 탭 편집, 견본), 서버(저장, 검사, 판, 카탈로그), 브리지(맥 안 주소), 스킬 |
| 2 | "매일 아침 갱신해 줘"가 되고, 덱 데이터를 바로 가리키고, 버튼을 누르면 에이전트에게 말이 간다 | 서버(데이터 묶음), 앱(`$data` 풀기, 갱신 시각) |
| 3 | 조립 부품, 그다음 격리 부품 | 앱, 서버, 카탈로그 |

1단계의 첫 시험 화면은 실제 수익 탭으로 한다. 수익 데이터를 어디서 가져올지(앱스토어 커넥트, 광고 대시보드, 직접 입력)는 에이전트와의 대화에서 정하고, 1단계에서는 숫자를 대화로 직접 알려 줘도 된다.

## 나중에 더할 것

탭 스토어를 둔다. 사용자가 만든 탭 화면(설계도와 견본 데이터)을 올려 다른 사람과 나누고, 다른 사람이 올린 탭을 검색해서 내 에이전트의 탭에 추가하는 곳이다. 지금 견본 창이 앱에 박아 둔 목록이라면, 스토어는 그 목록을 사람들이 채우는 셈이다. 설계도는 이미 부품 이름과 값만 담은 JSON이고 서버가 카탈로그로 검사하므로, 남이 만든 설계도를 받아도 그리는 쪽에서 위험한 일은 생기지 않는다. 데이터 묶음은 나누지 않는다. 받은 탭은 빈 틀로 들어오고, 숫자는 내 에이전트가 채운다. 정할 것은 올리는 사람 표시와 신고, 버전이 바뀐 설계도를 받은 쪽에 어떻게 알릴지다. (2026-11-12 기록)

## 열린 질문

격리 부품(3단계)이 스스로 인터넷에 접속하게 둘지 정해야 한다. 격리 부품은 에이전트가 HTML로 만든 작은 웹 페이지다. 막으면 에이전트가 넣어 준 데이터 묶음만 그릴 수 있어 데이터가 밖으로 새지 않지만, 지도처럼 외부 서버에서 그림을 계속 받아 와야 하는 부품은 만들 수 없다. 지금 생각은 기본으로 막고, 부품이 접속할 주소를 미리 밝히고 사용자가 한 번 승인한 주소만 열어 주는 것이다.
